# Open Sprinkler 3.0 architecture

## Goals

Version 3.0 will replace the CGI scripts and private TCP command protocol with
one local-first application that owns the web interface, schedules, API, and
GPIO hardware. The tested `v2.0.0` release remains the rollback point while
3.0 is developed on a separate branch.

The design must:

- leave every active-low relay de-energized during startup and shutdown;
- prevent more than one process from owning the GPIO lines;
- serialize all relay commands and allow only one active station;
- automatically stop every manual or API run after a bounded duration;
- provide a versioned API for the web interface and Home Assistant;
- keep credentials and mutable data outside the application directory;
- continue running without cloud services or an internet connection.

## Process model

The application runs as one Python ASGI process with exactly one Uvicorn
worker. FastAPI handles HTTP requests, and an asyncio command queue serializes
all access to the relay backend. Multiple Uvicorn workers are forbidden because
each worker would create an independent controller and compete for the same
GPIO lines.

The controller is the only component allowed to call the GPIO Zero relay
backend. It turns all relays off before energizing a station, and every start
command includes an automatic shutoff duration.

```text
Browser or Home Assistant
          |
          v
lighttpd reverse proxy and TLS
          |
          v
FastAPI /api/v1, one Uvicorn worker
          |
          v
serialized asyncio command queue
          |
          v
GPIO Zero + lgpio + active-low relay board
```

## API contract

The current development branch implements:

- `GET /api/v1/health`, unauthenticated liveness check;
- `GET /api/v1/status`, station and active-run state;
- `POST /api/v1/stations/{id}/start`, start one station for a required number
  of seconds;
- `POST /api/v1/stations/{id}/stop`, stop one station;
- `POST /api/v1/actions/stop-all`, de-energize every relay;
- `POST /api/v1/auth/login`, exchange the API token for a signed browser
  session;
- `POST /api/v1/auth/logout`, clear the current browser session;
- `GET|POST /api/v1/schedules`, list and create schedules;
- `PUT|DELETE /api/v1/schedules/{id}`, replace or remove a schedule;
- `GET|PUT|DELETE /api/v1/rain-delay`, inspect, set, or clear a delay;
- `GET /api/v1/history`, retrieve bounded station-run history.

Control and status endpoints require either an `Authorization: Bearer` header
or a signed browser session. The token is read from a root-managed file, must
contain at least 32 characters, and is never accepted in a URL, stored in Git,
or written to logs. The web dashboard exchanges it for an HttpOnly session,
and state-changing browser requests also require a CSRF token. TLS termination
and rate limiting belong at the lighttpd reverse-proxy boundary.

The OpenAPI document generated by FastAPI is the machine-readable API
contract. Breaking changes require a new API prefix, such as `/api/v2`.

## Home Assistant

REST is the foundational integration because it works with a stock Home
Assistant installation and does not require an MQTT broker. Home Assistant can
poll `/api/v1/status` and call the POST actions with a bearer token stored in
`secrets.yaml`. A starter example is in
[`home-assistant/rest.yaml`](home-assistant/rest.yaml).

Optional MQTT support is planned after the controller and persistence layers
are stable. It will use Home Assistant MQTT discovery to publish one valve
entity per station, controller availability, and active-run state. MQTT will
be an adapter over the same controller API, not a second path to GPIO.

A custom Home Assistant integration is not part of the first 3.0 release. It
would add packaging and maintenance cost before the device API has stabilized.

## Configuration and persistence

Target filesystem locations are:

- `/etc/open-sprinkler/open-sprinkler.ini` for hardware and service settings;
- `/etc/open-sprinkler/api-token` for the API bearer token;
- `/var/lib/open-sprinkler/open-sprinkler.db` for schedules and run history;
- `/run/open-sprinkler/` for temporary lgpio files.

SQLite stores schedules, delays, controller state, and run history. It provides
transactions and avoids concurrent INI rewrites. Schedule claims are atomic
and limited to one run per local date. A bounded grace window avoids starting a
morning program hours late after a long outage. Any unfinished station run is
marked `interrupted` when the application initializes after a restart.

GPIO pin assignment stays in the root-managed configuration because changing
it is a deployment operation, not routine sprinkler scheduling.

## Migration phases

1. **Controller and API, complete:** serialized commands, required automatic shutoff,
   bearer authentication, status, tests, and Home Assistant REST examples.
2. **Persistence and scheduler, complete:** SQLite schema, reliable schedule
   evaluation, run history, rain delays, and restart recovery.
3. **Web application, complete:** responsive interface using only `/api/v1`,
   with signed browser sessions, CSRF protection, and no state-changing GET
   requests.
4. **Deployment, in progress:** dedicated service account, hardened systemd
   unit, lighttpd reverse proxy, HTTPS guidance, and a fresh-system acceptance
   procedure are implemented. Target-Pi acceptance, backup, and v2 data
   migration remain.
5. **Home Assistant discovery:** optional MQTT adapter and discovered valve
   entities, without making MQTT a core dependency.

Production acceptance will use a separate Raspberry Pi 4 with a clean
Raspberry Pi OS Lite 64-bit Trixie image. The working 2.0 controller remains
untouched until the 3.0 deployment phase passes relay tests with valve power
disconnected.

## Explicit non-goals for the first milestone

- replacing the existing v2 installation on a live controller;
- Docker or multiple service processes;
- internet or cloud dependence;
- remote GPIO access;
- MQTT as a required dependency.
